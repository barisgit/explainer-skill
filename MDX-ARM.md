# MDX + Preact arm: design contract

Spike branch `spike/mdx`. Every lane reads this file; the main agent owns it. Background: `/Users/blaz/Programming_local/Projects/artifact-lab/arms/MDX-SPIKE.md`.

## Goal and fairness

An agent writes a page as MDX (Markdown prose plus components) with local data files it imports; `pack page.mdx -o index.html` compiles it at pack time, prerenders it to static HTML with Preact, and inlines only the client code and props the interactive parts need. One self-contained offline file, same `theme.css`, same `check`, same content rules as the v0.8 attribute kit. The arm must be neither weaker nor carry extra guidance than v0.8: only the authoring mechanics differ.

## Architecture

- **The runtime stays the attribute kit.** `kit/views.ts`, `steps.ts`, `reply.ts`, `link.ts`, `charts.ts`, `echarts.js` and `theme.css` (with their parts) are the tested v0.8 behaviour and are not rewritten. The kit's Preact components are typed markup generators over that runtime: they render the same attribute markup v0.8 pages write by hand (`section.view[data-view]`, `[data-stepper]` with `[data-captions]`, `fieldset[data-reply]`, `.tree` of nested `<details>`, `.chart`), and pack inlines the kit scripts the prerendered page needs. Re-syncing to v0.8.0 is then mostly copying kit files.
- **Static by default.** Everything in the MDX renders once at pack time; static components may take any props (functions included) because they run only in pack.
- **Islands.** A module whose first statement is `"use client"` is a client component: its capitalised function exports are hydrated in the browser. On the server they render to HTML between comment markers (`<!--island:N-->…<!--/island-->`, hydrated with a root fragment, no wrapper element, so the theme's child selectors still match). Props crossing from MDX into an island must be JSON; pack fails with the prop path otherwise, and tells the author to move function-holding code into their own client component. An island inside an island renders as a plain component of its parent. Children from MDX into an island are refused (pass text as a prop, or write the content inside the component). An element with an `on*` function prop rendered outside every island fails the pack, naming the element and the component that renders it. Islands hydrate before the kit scripts that read the DOM (views, steps, link, reply) run, so `reply.js` keeping (which dispatches input/change events on restore) and `steps.js` reach Preact-owned DOM; echarts, charts.js and plot.js load before the islands, because client components call `Charts.make` and `Plot.make`.
- **Kit components inside islands** wire their callbacks with effects: `Chart` and `Plot` call `Charts.make`/`Plot.make` on their element, `set()` on option changes and `dispose()` on unmount; `Stepper` listens for `stepchange` and calls `Steps.refresh` after renders. `Chart` and `Plot` are client modules, so one with a JSON option works straight from MDX; `Stepper` is not, so the page can hand it static parts, and inside a client component it is a plain part of that island.
- **Page shell** (pack writes it): `<html lang>`, `<title>`, `kit:theme.css`, the page's imported CSS, `<main class="page"><div data-overview>…</div>views…</main>`, the islands' props (`<script type="application/json" id="explainer-islands">`), `var kitLabels`, echarts and charts.js, the island bundle, then views, steps, link and reply. The overview `div` is written on every page, with or without views. Every rendered `<View>`, wherever the page renders it (top level, inside a section, or `{items.map(...)}`), is moved after the overview in page order. On the overview, `#` plus the paragraphs right under it form `header.masthead` (first paragraph `.lede`, later ones `.meta`); a View builds its `.view-head` the same way from its leading `h1` and paragraphs, with its `back` link first. Within the overview and each view, each `##` (or `<h2 data-nav="…">`) with what follows becomes a `<section>` unless the author already wrapped it in one.
- **Frontmatter** (YAML): `title` (default: the h1's text, else the file name), `lang` (default `en`), `labels` (kitLabels, same keys as v0.8), `reply: true` (include reply.js for notes and keeping on a page with no question; a `data-reply` in the page includes it by itself). Any other key fails the pack.
- **Mermaid**: a ```` ```mermaid ```` fence becomes `<pre class="mermaid">` and the existing in-process renderer draws it in the HTML pass.
- **Kit script inclusion** follows the prerendered HTML and the client bundle: echarts+charts when a `.chart` that is not a `.plot` renders or the client bundle holds the kit's Chart, plot.js for `.plot` or Plot, steps.js for `[data-stepper]` or Stepper, views.js for `[data-view]` or `<details>`, link.js for `[data-ref]`, reply.js for `[data-reply]` or `reply: true`.
- **Imports**: `preact`, `preact/hooks`, `preact/jsx-runtime` and `kit` (the components) resolve to vendored files, so the skill runs as copied with Bun and no install. Pages import `.json`/`.ts` data and `.css` like any bundler page; an imported `.mdx` file is a fragment, without the page layout.
- **After SSR**, the HTML goes through the existing pack pipeline unchanged (Mermaid, inlining, SVG theming, load detection). `pack page.html` keeps working as before.

## Rules for lanes

- Work only in `.worktrees/mdx`; never edit `main` or the other worktrees (`tree`, `reply-bar`, `guide8` are read-only references for v0.8 behaviour).
- Gates: `bun run typecheck`, `bun run lint` pass without weakening rules; `bun run test` stays green for tests that still apply. Commits follow AGENTS.md (Conventional Commits, explicit paths, never `--no-verify`); commit one worktree at a time (lint-staged stashes are shared).
- No private data in commits. Do not touch `~/.agents/skills/explainer/`.
- Agent-facing text (SKILL.md, guide.md, component doc comments, CLI help) stays short and soft, per AGENTS.md.

## As built (core lane)

- Files: `src/mdx/compile.ts` (frontmatter, MDX with GFM, Mermaid fences, layout), `src/mdx/structure.ts` (masthead, sections, views), `src/mdx/bundle.ts` (the prerender and client builds: bare imports, `.mdx`, CSS, the `"use client"` swap), `src/mdx/page.ts` (shell and kit scripts); `kit/islands/server.ts` and `client.ts` (the island runtime); `kit/components/` (`index.ts` is what `kit` resolves to; `kit components` prints its doc comment and each component's). Generated: `vendor/mdx.js`, `vendor/preact/*.js` (`bun run vendor`), licences in `kit/licenses/mdx.txt` and `preact.txt`.
- A new kit component is a module in `kit/components/` re-exported from `index.ts`, with a leading `Name: description` comment. When it needs a kit script that its first render does not reveal through the HTML, add it to `COMPONENT_SCRIPTS` in `src/mdx/page.ts`.

## As built (static components lane)

- `View`, `Tree`, `Question` in `kit/components/` render exactly the markup a v0.8 author writes; `test/mdx-kit.test.ts` holds an .mdx page equal, after whitespace, to the same page written by hand as v0.8 HTML, and the screenshots `check` takes of both are identical.
- Views are static and per record: `{people.map((p) => <View name="person" param={p.id} ...>)}`. A View renders inside an `<explainer-view>` marker that `hoistViews` in `src/mdx/page.ts` removes, moving the view after the overview; a View inside a View or inside a client component fails the pack. A client component filling a parameterised view through `Views.on` is not offered: data is known at pack time, and views.js builds crumbs, previous/next and the rail from the DOM as it shows a view, before Preact would re-render. Client components go inside a View.
- `Tree` takes the records and an optional `row` mapping (static, so a function is fine) and recurses; it pads every row to the tree's column count and fails the pack on a row that is both a link and a fold, or opens to nothing.
- `Question` ids are `name-value`, stable across packs, for reply.js keeping. A bare `data-*` attribute on an HTML element in MDX (`<fieldset data-reply>`) compiles to an empty value, as in HTML; JSX would write "true", which reply.js would take as the label.
- Short rail labels: a section heading written `<h2 data-nav="Price">The price is 40 €</h2>` starts a section like `##`, and its `data-nav` moves to the `<section>`. An explicit `<section data-nav>` wrapper keeps working.
- GFM tables become `table.compare`: the first body cell of each row is `<th scope="row">`, every other cell gets its column header as `data-label`, and a Markdown alignment is kept as an inline `text-align`. No `.scroll` wrapper: v0.8 uses it only for `compare table`, which an author writes as HTML.

## As built (interactive components lane)

- `Stepper` renders `figure.fig[data-stepper]` with the parts and `ol[data-captions]`; steps.js inserts its controls before the list and owns the step. Preact 10.29 moves only the children it inserts or reorders, so a re-render leaves the inserted `.player` (and the focus in it) in place, and it sets an attribute only when its prop changed, so steps.js's `is-on`/`is-now`, `data-live`, `role` and `tabindex` survive. A part whose `class` prop changes loses `is-on`/`is-now` for one commit; the layout-effect `Steps.refresh` re-applies them before paint. The stepchange listener is a layout effect, attached while the island hydrates, so `onStep` hears the opening announcement. Refresh fires `stepchange` only on a changed step or count, so `onStep` → render → refresh settles after one round.
- Runtime additions (additive, v0.8 behaviour unchanged): `Steps.refresh(el)` registers a `[data-stepper]` added after load (steps.js used to throw), so a Stepper a client component mounts later works; `Charts.make(...).dispose()` and `Plot.make(...).dispose()` give the components an unmount path (charts.js also stops a pending font load from mounting a disposed chart).
- The client build records only modules with code in the bundle (`keepBundled` in `src/mdx/bundle.ts`, from Bun's metafile): `import { Plot } from "kit"` loads every re-export of `index.ts`, and counting them all would put ECharts on a Plot-only page.
- Keeping inside islands needs no new mechanism: reply.js restores after hydration and fires input and change, which Preact's `onInput`/`onChange` take into state. The author's one rule (in `kit components`): give the control an id and set state in `onInput` or `onChange`; a value set only in `onClick` would be reverted by the next render.
- `test/mdx-islands.test.ts`: static Stepper over SVG parts; a client component with scenario radios, a slider and a checkbox around a Stepper with computed captions and a Chart redrawn per step (step, switch, End key, focus kept, stepchange sequence, `check --do`); a late-mounted Stepper and Chart and the Chart's dispose; Plot-only pages without ECharts, from the page and from the author's component; keeping through a reload and Clear.
