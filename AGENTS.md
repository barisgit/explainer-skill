# Explainer skill: agent instructions

An agent skill, `explainer`, that builds one self-contained, interactive HTML page (charts, diagrams, step-through figures, drill-down views, reader replies) that works offline from `file://`. The skill is a thin `SKILL.md` plus a CLI (`kit`, `pack`, `check`) that the agent drives. The agent writes the page as MDX (`page.mdx`, with `.tsx` client components and the `.ts`/`.json` data and `.css` it imports); `pack` prerenders it with Preact into one file.

## Requirements

- Bun 1.4.3 (`curl -fsSL https://bun.sh/install | bash`). The CLI uses Bun's built-in `HTMLRewriter` and `import.meta.dir`; there is no npm install step for users. `node skills/explainer/cli.ts` prints an install hint and exits 2.
- Google Chrome or Chromium for `check` (`CHROME=/path` overrides the search, which also finds agent-browser and Playwright downloads; CI uses the runner's Chrome). `src/chrome.ts` retries without the sandbox when Chrome reports none is usable.

## Layout

```text
skills/explainer/      the installable skill, copied as-is by installers: no dotfiles, tests or node_modules inside
  SKILL.md guide.md
  example/             the example page: page.mdx and the model it imports (typechecked with the kit)
  cli.ts               thin entry: Bun check, then imports src/main.ts (erasable syntax only, so node can run it far enough to explain)
  src/                 main.ts (dispatch, help), commands.ts (one spec per command), paths.ts, kit.ts (kit file names, TypeScript to script, the kit's CSS layer, labels), pack.ts, data-uri.ts (the images and fonts pack embeds), collisions.ts (page classes the kit styles too), loads.ts (what a packed page would still load, read through Bun's CSS parser), svg-theme.ts (svg files per colour scheme), ids.ts (repeated ids), check.ts, steps.ts, report.ts, mermaid.ts, chrome.ts (CDP client)
    mdx/               compile.ts (frontmatter, MDX with GFM, math, Mermaid fences), structure.ts (masthead, sections, views), bundle.ts (the prerender and client builds, imported images and fonts as data: URLs), page.ts (shell, view hoisting, kit scripts), client-loads.ts (files client code would load later), kit-scripts.ts (which kit script a page needs), math.ts (TeX to MathML), sources.ts (what kit types checks)
  kit/                 theme.css, math.css, and the kit scripts charts, plot, steps, link, views, keep and reply as .ts sources that pages name .js; echarts.js (generated), fonts/, licenses/
    parts/<name>/      pieces of a kit file too long for one file (a script, or theme.css by concern); pack puts them in front of kit/<name> in file name order, so a page still includes one file
    components/        what pages import from "kit": one Preact module per component, re-exported by index.ts (whose header is kit page); parts/ holds Explore's pieces and number formats
    islands/           server.ts (prerender: islands, slots), client.ts (hydration), bare-data.ts (bare data-* attributes, both sides)
  vendor/              generated by bun run vendor, never edited: beautiful-mermaid.js (patched, with ELK), mdx.js, math.js (remark-math, Temml) used by pack only; preact/ (bundled into pages with client components); types/ (the declarations kit types points at)
build/                 vendor.ts regenerates kit/echarts.js, vendor/ and the licence texts from the pinned devDependencies (*-entry.ts are the bundles' entries); geist-widths.ts measures the Geist advances the patch sizes diagram text with; verify-install.ts is the release check for the installers; media.ts (with media/) renders the README and gallery media
test/                  contract tests, outside the skill so installs do not ship them
  fixtures/mdx-all/    the acceptance page: every component and page convention, not published
kit-types/             globals.d.ts: the window globals the kit scripts define (and echarts); vendor copies it into vendor/types/ for author typechecking
examples/              the public gallery, published as it is committed by .github/workflows/pages.yml (push to main)
  page.mdx index.html  the gallery page and its packed output
  <name>/              one showcase page: page.mdx and its components and data (written by an agent following SKILL.md), index.html (packed)
  media/               generated by bun run media: hero, gallery thumbnails, README clips, each as <name>-light.webp and <name>-dark.webp
```

Root files: `package.json` (devDependencies only), `bun.lock`, `patches/` (the beautiful-mermaid patch, applied by `bun install`), `tsconfig.json` (the CLI, build and tests; Bun types), `tsconfig.kit.json` (the kit scripts, components and islands, and the example, fixture and gallery pages; DOM lib, no Bun types), `CHANGELOG.md` (what an author does differently, per release), `biome.json`, `bunfig.toml`, `.husky/`, `.github/workflows/ci.yml` and `pages.yml`.

Showcase assets stay in `examples/`, never in `skills/explainer/`, because installers copy the skill folder. After changing a page or the kit, repack the examples (`pack page.mdx -o index.html` from each directory), `check` each to 0 problems, then `bun run media`; GitHub renders the repo-relative animated WebP clips in the README, while a repo-relative `<video>` does not play. The README picks each image's theme with `<picture><source media="(prefers-color-scheme: dark)">`; the gallery shows both thumbnails and hides one with CSS, as the kit does for SVG files in `<img>`.

## Commands

| Command | What it does |
|---|---|
| `bun install` | Installs dev tools from the lockfile and the git hook (`prepare` runs husky) |
| `bun run typecheck` | `bun check --all` for the CLI, build and tests, then for the kit (`tsconfig.kit.json`): Bun's built-in checker, same errors as `tsc`, strictest settings |
| `bun run lint` | `biome check` (format check, lint, import order), warnings are errors; no writes |
| `bun run format` | `biome check --write`: formats and applies safe fixes |
| `bun run test` | Contract tests (Chrome needed, about two minutes) |
| `bun run ci` | typecheck, lint, test: the gate; the same command runs in GitHub Actions |
| `bun run verify:install` | Release check, not in `ci` (needs network and Chrome): installs from a clone of HEAD with `npx skills` and Caplet into a temp HOME, then runs `kit`, `pack`, `check` from each copy |
| `bun run media [--keep] [example ...]` | Regenerates `examples/media/` (gallery thumbnails, hero collage, animated WebP clips) in light and dark from the packed `examples/<name>/index.html` pages; a full run replaces the directory. Scenes are data at the top of `build/media.ts`. Needs Chrome and ffmpeg with libwebp_anim; about two minutes |
| `bun run vendor` | Regenerates the ECharts, beautiful-mermaid, MDX, math and Preact bundles, the vendored declarations and the licence texts (dev only) |
| `bun skills/explainer/cli.ts kit \| pack \| check` | The skill's CLI; `--help` on any command. `kit <Name>` prints one component's doc, `kit types` a tsconfig for a page directory, `kit labels` the kit's texts to translate |

The pre-commit hook (husky + lint-staged) runs Biome with fixes on the staged files, then the typecheck; about 2 s, no Chrome. It keeps partially staged hunks. lint-staged backs up through `git stash`, which worktrees share, so run commits of different worktrees one at a time. Never use `--no-verify`.

`.github/workflows/ci.yml` runs `bun install --frozen-lockfile` and `bun run ci` on ubuntu-latest. The runner restricts user namespaces, so CI exercises the no-sandbox retry.

## Decisions

- One skill named `explainer`: thin `SKILL.md` and the CLI as the toolbox; no custom elements; offline single-file output; the house style lives in `kit/theme.css` (with `kit/parts/theme/`) and `example/`, not in instructions.
- One authoring path: `pack` takes a `.mdx` page and refuses anything else with one line saying to write `page.mdx`. No flag or helper offers HTML as author input; already-packed HTML files still open offline and `check` takes them. Tests of the kit runtime may feed the pipeline after prerendering whatever keeps them simplest.
- Runtime is Bun only. Headless Chrome (CDP over WebSocket, no Puppeteer) for `check` only.
- Mermaid is rendered in-process by beautiful-mermaid with ELK: one SVG per diagram, drawn with the renderer's variables that `theme.css` maps to the kit tokens, so it follows light, dark and a page's overrides. The patch (`patches/beautiful-mermaid@1.1.3.patch`) lays out in reading order, sizes text with Geist's measured widths and wraps labels at Mermaid's 200 px. `pack` fails, with what to write instead, on types it cannot draw and on input the renderer would draw wrong silently. Diagrams do not step; linked highlighting walks through them.
- Layout is the packaging layout above: Caplet imports `skills/*/SKILL.md` as a bare skill and copies every non-hidden file. Do not add an `acf.yml`; it would make Caplet emit only the files listed in `assets:`.
- Agent-facing text (SKILL.md, guide.md, component and kit file headers, CLI help) stays short and soft. A component's or listed kit file's leading comment is its documentation: `kit <name>` prints it, and a component's first line (`Name: description`) is its listing line; the other features' lines (Mermaid, math, theme, link, reply, keep, page) are `FEATURES` in `src/commands.ts`. The listing stays within v0.8.2's size, 17 lines and 347 words, since authors read it before writing.
- The kit's CSS ships in `@layer kit` (`readKitText` wraps it, internal order kept), so a page's own unlayered CSS always wins and one plain rule overrides the kit. The kit's `!important` rules (`[hidden]`, reduced motion, print, the other copy of an SVG file) therefore also beat a page's `!important`. The kit's other properties still reach a page element that carries a kit class, so `pack` warns when a page rule styles an element by a class the kit styles on its own (`collisions.ts` states the rule); the documented classes are no exception, since `.tree` was one when a page's own `.tree` was restyled (#51).
- `pack` themes an SVG file in `<img>` without reading it as markup: the file stays an image (no script, network or page styling reaches it), packed twice as `img.light` and `img.dark` with a first `:where(:root)` rule that sets `color-scheme`, `color: var(--ink)` and the colour tokens copied from `theme.css`, and `theme.css` shows the copy for the scheme. A page's own token overrides do not reach the file; parts that must link or respond need inline SVG. An `<img>` a client component renders stays one image in the file's own colours (outside its slot), since Preact hydrates one element and drops a second copy.
- Credits stay: visual-explainer (MIT, Nico Bailon), ECharts (Apache-2.0), beautiful-mermaid (MIT, Craft Docs) with elkjs (EPL-2.0) and entities (BSD-2-Clause), Preact and preact-render-to-string (MIT), MDX (MIT) with the 116 other packages its bundle carries (MIT but for the ISC `@ungap/structured-clone`), Temml (MIT, Ron Kok) with remark-math, micromark-extension-math and mdast-util-math (MIT), `temml.woff2` (KaTeX fonts, MIT, Khan Academy), Geist fonts (OFL); their licence texts ship in `kit/licenses/` (`preact.txt`, `mdx.txt`, `math.txt` list each package with its version). EPL-2.0 needs the source statement in `elkjs.txt` and the notice in the bundle header, both written by `build/vendor.ts`.
- No local-only dependencies at runtime: nothing but `kit/` and `vendor/` is needed after install, and Chrome for `check`.

## Limits

Biome (pinned 2.6.2) enforces the quality baseline at error: cognitive complexity 15, function length 80 lines without blanks, file length 600 lines, no `any`, no non-null assertions, no `@ts-ignore`, no import cycles, no unused code. Suppressions need a rule-specific reason and are rare; today they are:

- `kit/*.ts` and `kit/parts/*/*.ts` (the kit scripts): each file is one IIFE (a part is one function that hangs on `window` for its entry) that keeps its names out of the page's global scope, so the function-length rule sees one long function. The code inside is split into small functions.
- `kit/theme.css` and `kit/parts/theme/*.css`: deliberate `!important` overrides (`[hidden]`, reduced motion, print) and selector orders whose properties are disjoint. Biome compares specificity only within one file, so the order across parts is checked by eye: the parts keep the cascade order of one stylesheet, and `theme.css` comes last.

Excluded by path: `kit/echarts.js`, `kit/parts/math/temml.css`, `vendor/` bundles and declarations (generated), HTML and Markdown.

TypeScript uses `erasableSyntaxOnly`: no parameter properties, enums or namespaces, so node can strip types in `cli.ts` and Bun's transpiler can strip them from the kit.

## The kit scripts

The kit scripts are TypeScript sources. Authors never name them: `src/mdx/kit-scripts.ts` picks the ones a page's markup needs, and the page shell refers to each as `kit:<name>.js` internally. `src/kit.ts` maps that name to the `.ts` file and `pack` strips the types with `Bun.Transpiler` as it inlines it: the output is a plain classic script (no imports, exports or module wrapper), with the file's leading `/* ... */` documentation comment put back in front, because the transpiler drops every comment. `kit <feature>` (for example `kit keep`) prints that comment from the source for the scripts the `kit` listing names; the others are documented through the components that bring them. Keep a kit file a script: no top-level `import` or `export`, no generated `.js` next to the source. Bun's transpiler is not a pure type eraser: it drops a `"use strict"` directive, rewrites top-level `this`, and adds an import for decorators, so the kit uses none of these and wraps its code in a function or assigns to `window`.

`tsconfig.kit.json` checks them with the DOM lib, no Bun types and the same strict options as the rest, except `noPropertyAccessFromIndexSignature`: `element.dataset` has an index signature, so the option would turn every `dataset.ref` into `dataset["ref"]`, which Biome's `useLiteralKeys` rejects. The window globals the scripts define (`Charts`, `Plot`, `Steps`, `Views`, `Keep`, `ReplyNotes`) and `echarts` are declared once in `kit-types/globals.d.ts`, with the option and callback types of their public API. Authors can typecheck their own `.tsx` with `kit types > tsconfig.json` then `bun check`; the generated config resolves the components and the vendored Preact, ECharts and kit declarations without an install.

## The MDX pipeline

- **The runtime stays the attribute kit.** The kit scripts and `theme.css` are the tested behaviour; the components in `kit/components/` are typed markup generators over them, rendering the markup the scripts read (`section.view[data-view]`, `[data-stepper]` with `[data-captions]`, `fieldset[data-reply]`, `.tree` of nested `<details>`, `.chart`). Keep runtime changes additive.
- **Static by default.** Everything in the MDX renders once at pack time, so static components take any props, functions included, except `onX` handlers, which would never run: pack fails on one made outside every island, naming the element and prop.
- **Islands.** The capitalised exports of a module whose first statement is `"use client"` hydrate in the browser. They render between `<!--island:N-->…<!--/island-->` with no wrapper element, so the theme's child selectors still match. Props from the page must be JSON or functions a `"use client"` module exports (pack fails with the prop path otherwise). Markdown between an island's tags is its slot: rendered once to static HTML, placed exactly once with `{children}`, and left untouched by re-renders; a `##` first in it starts the enclosing section. A kit client module (Chart, Plot) may sit in a slot as an island of its own; the author's own client component may not. echarts, charts.js and plot.js load before the islands; views, steps, link, keep and reply after, so they reach Preact-owned DOM and keep's restore fires the input and change events Preact's handlers read.
- **Page shell and structure.** pack writes `<html lang>`, the title, the theme, the page's CSS, `<main class="page"><div data-overview>…</div>views…</main>`, the islands' props as JSON, `kitLabels`, then the scripts. `#` plus the paragraphs under it form `header.masthead`; each `##` (or `<h2 data-nav>`) with what follows becomes a `<section>` unless the author wrote one; every rendered `View` moves after the overview. A GFM table becomes `table.compare` (first cell `<th scope="row">`, `data-label` per cell, `---:` columns `.num`).
- **Frontmatter:** `title`, `lang`, `labels` (`kit labels` prints every key), `reply: true` (notes on a page with no question), `scheme: light | dark`; any other key fails. pack warns on a non-English `lang` without `labels`.
- **Kit scripts follow the markup.** `src/mdx/kit-scripts.ts` is one table of the markup each script reads, matched over the prerendered HTML and over the client bundle, so a component's code brings what it can render and tree shaking keeps unused components out (a Plot-only page carries no ECharts). A new component needs a row only for an attribute or global no script read before; `kit` sizes each component by the same table. Markup built from computed names is not found.
- **Imports** `preact`, `preact/hooks`, `preact/jsx-runtime` and `kit` resolve to vendored files, so the skill runs as copied. An imported `.mdx` file is a fragment without the layout. An imported image or font is its `data:` URL, and any other imported file fails `pack`, so client code carries what it shows; the HTML pass sees only the prerendered page, so a file path written in client code, an island's props or a filled record's markup fails `pack` (`src/mdx/client-loads.ts` states what it finds).
- **Views: static or filled.** A `View` with a `param` is prerendered once per record and prints; a filled view (`records`, `render` from a client module) carries the records once as JSON, draws only the open record, and prints only while open. A View inside a View, inside a client component or in a filled record fails the pack. pack draws every filled record once and checks its markup as it checks the page's: what it loads (`client-loads.ts`) and its ids, within the record and against the page's own (records show one at a time, so not against each other).
- **Keeping needs no reply:** a control with an id brings keep.js; reply adds notes, answers and the Clear button. Ids repeated in the prerendered page or in a filled record fail `pack`, naming each place (`src/ids.ts`); `check` reports them on pages packed elsewhere. `Question` ids are `name-value`, other characters written `_hex_`.
- **Math** renders at pack time to MathML with Temml: no script ships, display math scrolls sideways on a phone, `kit/math.css` comes only with a page that has math. `Explore` precomputes frames when its `frame` is not a client export, refusing over 100,000 JSON characters.
- **A new component** is a module in `kit/components/` re-exported from `index.ts`, with a leading `Name: description` comment (the listing line; `kit <Name>` prints the comment). `test/mdx-islands.test.ts` fails for an export without a use in `COMPONENT_USES`, and for one whose later render brings fewer scripts than its static render. `test/fixtures/mdx-all/` should use it.

## Installing

Verified with `npx skills` 1.7.4 and Caplet 0.1.0 (the first npm release, `@caplet/cli`): both copy every file byte for byte (npx skills symlinks the other agents to one canonical copy when several are chosen), and `kit`, `pack`, `check` and the example's `kit types` + `bun check` run from the installed copy with no install step. `bun run verify:install` repeats this from a clone of HEAD (uncommitted changes are not tested); run it before a release and whenever `skills/explainer/` changes shape (new top-level file, dotfile, `package.json`).

npx skills installs from any public git repository; the skills.sh listing comes from its install telemetry, so the skill appears there after people install it. Caplet takes `github:<owner>/<repo>` or `git:<url>` with a required `--pin <ref>`: a branch to follow or a tag for a fixed version.

Trying an installer by hand: always give it a disposable HOME (installers write to `~/.agents`, `~/.claude` and, for npx skills, `~/.agents/.skill-lock.json`), with `DISABLE_TELEMETRY=1` and `CLAUDE_CONFIG_DIR` unset. Caplet quirks that matter:

- A project-scope Caplet command with no `.agents/` in the project walks up the directory tree. A sandbox below the real home therefore finds the real `~/.agents` and writes to it. Run `caplet init` in the project first (`verify-install.ts` does).
- `caplet add` does not detect that another capability already emits a skill of the same name. Both write into one directory, the files mix, and `caplet check` stays stale. Retire the other source first.
- A local-path source is snapshotted: after changing the checkout run `caplet update explainer`, not `caplet apply`.
- Caplet rewrites `SKILL.md`'s frontmatter as YAML folded at 80 columns with no blank line after it. `SKILL.md` is kept in that form so Caplet's copy stays byte-identical; after editing the description, run `verify:install` or fold it the same way.
- Caplet gives Claude Code the skill as a plugin, not as `~/.claude/skills/explainer`: the copy Claude Code loads is the `installPath` in `~/.claude/plugins/installed_plugins.json` (plus `skills/explainer`), which `verify-install.ts` reads.

## Changing the kit

Kit files are behaviour, not just code. After a change: `pack` then `check` `skills/explainer/example/page.mdx` and a few real pages (light and dark, 1440 and 390 wide are covered by `check`), open the screenshots, and compare with the previous output. Pages reference local files relative to themselves, so pack them from where they are with `-o` elsewhere.

## Tracking

Open work lives in [GitHub Issues](https://github.com/barisgit/explainer-skill/issues), not in files. File a finding as an issue with the symptom, `Path:`, `Suspected cause:` and what counts as done. Label it with one `type:`, its `area:` labels (`kit`, `cli`, `check`, `pack`, `install`, `ci`), a `priority:` or `status:deferred`, and `invariant` when it breaks a decision or promise in this file or the docs; `status:needs-decision` marks an issue waiting on a product choice. A fixing commit closes its issue. Deferred issues are not authority to build.

## Commits

Conventional Commits (`feat(kit):`, `fix(check):`, `chore:`, `test:`, `docs:`), one change per commit, explicit paths when staging. Gates pass on every commit. The public remote is `github.com/barisgit/explainer-skill` (MIT); releases are tags such as `v0.1.0`, which Caplet installs pin.
