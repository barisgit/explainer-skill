# Explainer skill: agent instructions

An agent skill, `explainer`, that builds one self-contained, interactive HTML page (charts, diagrams, step-through figures, drill-down views, reader replies) that works offline from `file://`. The skill is a thin `SKILL.md` plus a CLI (`kit`, `pack`, `check`, `serve`) that the agent drives. The agent writes the page as MDX (`page.mdx`, with `.tsx` client components and the `.ts`/`.json` data and `.css` it imports); `pack` prerenders it with Preact into one file.

## Requirements

- Bun 1.4.3 or newer; CI pins 1.4.3 (`curl -fsSL https://bun.sh/install | bash`). The CLI uses Bun's built-in `HTMLRewriter` and `import.meta.dir`; there is no npm install step for users. `node skills/explainer/cli.ts` prints an install hint and exits 2.
- Google Chrome or Chromium for `check` (`CHROME=/path` overrides the search, which also finds agent-browser and Playwright downloads; CI uses the runner's Chrome). `src/chrome.ts` retries without the sandbox when Chrome reports none is usable.

Root files: `package.json` (devDependencies only), `bun.lock`, `patches/` (the beautiful-mermaid patch, applied by `bun install`), `tsconfig.json` (the CLI, build and tests; Bun types), `tsconfig.kit.json` (the kit scripts, components and islands, and the example, fixture and gallery pages; DOM lib, no Bun types), `tsconfig.records.json` (the records core; ESNext lib only, so neither DOM nor Bun reaches it), `CHANGELOG.md` (what an author does differently, per release), `CLAUDE.md` (imports this file for Claude Code), `biome.json`, `bunfig.toml`, `.husky/`, `.github/workflows/ci.yml` and `pages.yml`.

Showcase assets stay in `examples/`, never in `skills/explainer/`, because installers copy the skill folder. After changing a page or the kit, repack the examples (`pack page.mdx -o index.html` from each directory), `check` each to 0 problems, then `bun run media`; GitHub renders the repo-relative animated WebP clips in the README, while a repo-relative `<video>` does not play. The README picks each image's theme with `<picture><source media="(prefers-color-scheme: dark)">`; the gallery renders each page's own `opening.mdx`, so its figures use the kit's theme directly.

## Commands

| Command | What it does |
|---|---|
| `bun install` | Installs dev tools from the lockfile and the git hook (`prepare` runs husky) |
| `bun run typecheck` | `cmp` of `kit-types/globals.d.ts` with its vendored copy (`bun run vendor` copies it), then `bun --check` for the CLI, build and tests, then with `--tsconfig-override` for the kit (`tsconfig.kit.json`) and the records core (`tsconfig.records.json`): Bun's built-in checker, same errors as `tsc`, strictest settings |
| `bun run lint` | `biome check` (format check, lint, import order), warnings are errors; no writes |
| `bun run format` | `biome check --write`: formats and applies safe fixes |
| `bun run test` | Contract tests (Chrome needed, about six minutes) |
| `bun run ci` | typecheck, lint, test: the gate; the same command runs in GitHub Actions |
| `bun run verify:install` | Release check, not in `ci` (needs network and Chrome): installs from a clone of HEAD with `npx skills` and Caplet into a temp HOME, then runs `kit`, `pack`, `check` from each copy |
| `bun run media [--keep] [example ...]` | Regenerates `examples/media/` (README hero clip, opening-screen cards and interaction clips) in light and dark from the seven packed `examples/<name>/index.html` pages; a full run replaces the directory. Scenes are data at the top of `build/media.ts`. Needs Chrome and ffmpeg with libwebp and libwebp_anim on PATH; keep the machine awake while recording |
| `bun run vendor` | Regenerates the ECharts, beautiful-mermaid, MDX, math, Preact and TanStack Table bundles, the vendored declarations and the licence texts (dev only) |
| `bun skills/explainer/cli.ts kit \| pack \| check \| serve` | The skill's CLI; `--help` on any command. `kit <Name>` prints one component's doc, `kit types` a tsconfig for a page directory, `kit labels` the kit's texts to translate |

The pre-commit hook (husky + lint-staged) runs Biome with fixes on the staged files, then the typecheck; about 2 s, no Chrome. It keeps partially staged hunks. lint-staged backs up through `git stash`, which worktrees share, so run commits of different worktrees one at a time. Never use `--no-verify`.

`.github/workflows/ci.yml` runs `bun install --frozen-lockfile` and `bun run ci` on ubuntu-latest. The runner restricts user namespaces, so CI exercises the no-sandbox retry. A step before the tests launches Chrome once: a fresh runner's first launch takes 6 to 17 s and sometimes over `check`'s 20 s deadline (#107), the 20 s staying for users.

## Decisions

- One skill named `explainer`: thin `SKILL.md` and the CLI as the toolbox; no custom elements; offline single-file output; the house style lives in `kit/theme.css` (with `kit/parts/theme/`) and `example/`, not in instructions.
- One authoring path: `pack` takes a `.mdx` page and refuses anything else with one line saying to write `page.mdx`. No flag or helper offers HTML as author input; already-packed HTML files still open offline and `check` takes them. Tests of the kit runtime may feed the pipeline after prerendering whatever keeps them simplest.
- Runtime is Bun only. Headless Chrome (CDP over `--remote-debugging-pipe`, no Puppeteer) for `check` only. The pipe makes Chrome exit with the process that drives it, however that process ends; a Chrome driven over a port outlived a killed `check` and spun a core. Chrome runs in a process group of its own, so a terminal's Ctrl-C reaches `check` alone, with a directory of its own for its profile and temp files (`TMPDIR`, and `MAC_CHROMIUM_TMPDIR` on macOS, where Chrome ignores `TMPDIR`; Google Chrome leaves a directory there on every launch), which is deleted only once every process of that group has exited (helpers outlive the main process by milliseconds and write into it); a group that outlives one SIGKILL leaves that directory in place with a warning, rather than holding `check` up. Chrome is stopped by closing the pipe and waiting for its exit (3 s), and only then by SIGTERM and SIGKILL: on macOS Chrome makes a `com.google.Chrome.code_sign_clone` copy of its whole app (about 1,340 files) under `/var/folders/<user>/X/` on every launch and removes it only on a clean exit, so a signalled Chrome leaves one per launch (#112); a signal to `check` itself still ends in the same order. `check` opens its page in Chrome's default context: with a page in a context of its own and a request in flight, a Chrome whose pipe closed (a killed `check`) kept spinning instead of exiting. Every DevTools call, load and start-up has a deadline that names what it waited for, and `check` waits on what the page draws (`SETTLE_JS` in `src/page-js.ts`: frames, fonts, visible charts, short timers), never a fixed time.
- DevTools loads match the main-frame commit and lifecycle load by loader, retaining events before command replies; reload guards the committed loader and follows its first reload candidate, while same-document navigation needs no new load. Steps execute their action once: only repeatable settlement and feedback cleanup may run again after an observed replacement document commits and loads, within the existing load budget. A canceled document request leaves the committed page usable but cannot explain a lost execution context; page exceptions, unexplained context loss and closed targets still fail.
- The default control sweep runs once on the light-desktop overview, not once per screen or view, and skips `--quick` and explicit `--do`. It samples visible, enabled initial-state controls, one per role/component up to 12, prioritizing the first of each kind and then the rest in document order: finite stepper navigation (Next, else Back), Plot's DOM legend, Question choices and answer disclosures, tree folds and Expand all, Records view/facet choices, Explore choice/toggle controls and an axis choice's strip, and one fragment link per view name (state after the first `?` is ignored for route matching, shared with view discovery). Hidden/revealed controls are not recursively explored; autoplay, ranges, graphical ECharts legends, arbitrary author controls and reset/download/reply actions need explicit `--do`. One 8 s ceiling includes creation and disposal (6 s work, 2 s reserved cleanup), not a new allowance per control. Each click uses the existing indexed `--do click` machinery from a fresh load, with local and tab session storage cleared from a loaded, script-free file document in the same tab, after the previous page unloads and before author scripts run (explicit `--do reload` keeps both); these loads do not run the scroll sweep. Reset-contract tests read storage after load; Keep tests exercise its actual restore. First-inline file-storage diagnostics stay separate (#148), rather than making browser binding timing part of the reset contract. Findings on the light-desktop overview name the control; incomplete coverage warns once with completed/total sampled clicks and the cap or budget. No per-control PNGs: use `--do` to inspect a failing state. A disposable default-context tab keeps control work away from the screenshot page. Creation replies remain owned through cancellation; a known target starts closing even while attachment is pending, and confirmed destruction releases that pending acquisition. Cleanup waits for target destruction; if closure cannot be confirmed within the ceiling, check fails rather than continuing with a live target.
- Pointer steps use unsigned-integer viewport pixels after preceding scrolls. `hover:<css>` scrolls to its target and hovers its centre; `drag:x,y-x,y` uses only points, matching point clicks without a second CSS-offset grammar. A drag dispatches a bounded sequence of held left-button moves and releases in `finally`, so canvas dataZoom sliders are exercised without series/data-index targeting. Click/drag feedback uses native event targets, their chart containers, a few observed public ECharts event names and hash changes; it reads no chart options, mark data or pixels and does not claim a full state diff. Notes carry theme/size, with at most three short target labels rather than a data dump. Host-held observations survive full-document navigation; the step-local browser binding and listeners are removed after settling. Executed steps keep their hit notes alongside any later settling problem; actions that never execute have no hit note. If a native point click opens a new opener-linked Chrome page target, its finding reports the opened window rather than an animation-frame wait. Cleanup closes only newly observed targets whose opener is the checked page, confirms they are gone within a short deadline (or stops the check), and restores the checked page to the foreground. A same-page `_self` navigation follows the existing document-load rules.
- Full-page `check` PNGs are document overviews: viewport-sticky boxes return to their flow positions and viewport-fixed overlays are hidden only during capture, without scrolling, resizing or changing interaction state. Scoped fixed boxes stay. The kit's contents rail (`.page > nav.toc`) is omitted silently because first-screen shots already show this known chrome (the Reply bar is in the page's flow and captured like the rest); visible author-fixed omissions still warn and can be captured with `--do shot:<css>` (#45, #178).
- The reply channel (#247): the page is outbound only and never knows its id or version; the endpoint it posts to carries them (`/api/pages/<id>/replies`, `?version=N` when served). One mechanism gives a page its endpoint: the slot `<meta name="explainer-reply-to">`, which pack writes among the head's leading meta elements on every page with reply.js (naming `replyTo` as the URL parser writes it, absolute http(s) without credentials, or empty) and the handler fills when it serves the page, matched from the document's start through meta elements only so no script or body text is taken for it; an empty one is clipboard only, and a page without the slot (no reply.js, or an older kit) cannot Send, so `publish()` and `serve` refuse it, saying to repack. The contract is `src/reply/protocol.ts`: envelope `{ v: 1, id, reader?, reply: { markdown, notes, answers } }`, hand-written guards naming the first bad field (no dependencies), unknown fields dropped, at most `MAX_BODY` (1 MB of UTF-8, 413 beyond, read in chunks); the server stamps `page`, `version` (a positive safe integer, null for a `replyTo` copy) and `time`, and a repeated `id` stores once (201 new, 200 the stored one, both JSON naming the id: the receipt); storage that cannot keep a reply throws and the handler answers 503, file storage leaving nothing of it behind. The handler and protocol use web standards only (the kit typecheck proves it through `kit-types/reply-protocol.ts`), so a host runs the same handler, which serves every page its storage holds; Bun lives in `serve` and file storage. The handler allows any origin (a `file://` page sends `Origin: null`) and has no publish route: publishing is the library's `publish()` (a new version only when the HTML changed, one call per id at a time: the caller's contract), since accounts and auth are out of scope (#32). `serve` listens before it publishes (a serve that cannot listen changes nothing another serve is serving, and its routes answer only once its page is published), serves its own id only (other pages in the data directory stay unserved and their replies are not taken), binds 127.0.0.1 on a fixed default port (4747), or with an opt-in `--host` another address for a team on the same network (printing this machine's network address for an any-address, and a line that the anonymous API is for a trusted network only), and serves the id at one URL (`/pages/<id>`), because keep's storage key is the URL without query, so unsent answers carry over a republish. It watches the file before its first read and publishes through one queue, so no edit is missed and none publishes over a newer one; a failed publication is reported and keeps the version served. It prints each reply on stdout as it arrives, a header line then the Markdown indented two spaces with control characters and U+2028/U+2029 escaped, so no reply line reads as a header (stderr says what it serves); `--wait` takes one reply, admitting replies one at a time (a check and its write finish before the next; a repeated id or a failed write leaves the place free; a later new reply gets 503 and stays with its reader) and then stops; it keeps each as `<time>-<id>.md` and `.json` in `<data>/<page id>/` beside `page.json`. Copy and Send are separate dialog actions: Send shows only with an endpoint and clears nothing (user, 2026-11-20: clearing would be annoying). It says "Sent." only for the receipt, "Send failed" for a 4xx and "Could not confirm delivery" otherwise (no answer, no whole response within one 15 s deadline, 5xx, a redirect, which it does not follow, or any other response), since the reply may have been stored. The envelope id is a hash of a per-browser salt and the reply's content (its JSON as Send builds it): sending an unchanged reply again, after a failure, a stored send, a reload or from another tab, gives the same id with no coordination or history, so the server stores it once; a changed reply gets another; two readers' equal replies differ by their salts. The id is cyrb128 (128 bits from four mixed 32-bit lanes; not cryptographic, since plain http on a LAN has no crypto.subtle). The salt (localStorage `explainer-reply-salt`, random, made once, read at each send; held in memory when storage refuses it) is all the browser keeps, never the reply. Known limit, accepted (user, #248 review round 3): two tabs that both send at the very first instant, before either kept a salt, each make one, so one reply can be stored twice, at most once per browser; atomic first use on plain http would need a coordination layer not worth it. One builder (`ReplyNotes.body()`) makes the body Send posts and `check --do reply` validates as the server would (size, JSON, guard). The optional reader name is remembered in localStorage `explainer-reader`. The `reply` event and `explainer:reply` postMessage stay on Copy; no frame is built (decided separately).
- `check --do reply` reads `ReplyNotes.markdown()` from the reply script’s existing builder without opening a dialog, using the clipboard or delivering to a host. Text and JSON preserve the Markdown per action ordinal/theme/size, including repeated captures; older exports without the API need repacking. It also validates `ReplyNotes.body()`, the text Send posts, as a reply server reads it (UTF-8 size, JSON, the protocol's guard) and reports a failure as a problem; an export from before Send has no body and is not checked.
- Mermaid is rendered in-process by beautiful-mermaid with ELK: one SVG per diagram (a flowchart or state diagram wider than a phone's 326 px column adds a copy laid out across its direction when that is narrower, which `theme.css` shows below 40rem, so a phone shrinks its text less, and in print when the wide layout would be too small to read; a Stepper's diagram gets it as any other), drawn in the plain look: no node fill, 1 px edges, edge labels as plain text on the tone masking the line, every text at the 13 px label role, boxes sized from Geist at that size, and never drawn larger than that, with the renderer's variables that `theme.css` maps to the kit tokens, so it follows light, dark and a page's overrides. The patch (`patches/beautiful-mermaid@1.1.3.patch`) lays out in reading order, sizes text with Geist's measured widths (`src/geist.ts`, which `build/vendor.ts` bundles in) and wraps labels at Mermaid's 200 px. Fan-in and fan-out keep ELK's routes when a shared trunk or any of its branches would enter a node box. `pack` fails, with what to write instead, on types it cannot draw and on input the renderer would draw wrong silently. Diagrams step through refs: a Stepper names the refs each step shows, as it names any part of the page.
- A system drawing is a Mermaid flowchart, not a component or a second dialect: number tags are fence meta (`tag:inv=2`), so the source stays plain Mermaid, as code fences take `ref:` marks. The patch draws a tag as a ring of 13 px text inside its node, before the label, and sizes the node for both, so the layout stays exact (a badge outside the box would cross edges ELK routes 12 px away). A tag is the node's ref, with `data-tag`, the one diagram part link.js makes focusable. A tag is named by its number and its node's label (`aria-label`). A mention is plain linked text: a phrasing element outside every SVG with one tagged ref whose text is that number gets `data-tag` from pack (`src/tags.ts`) and the same ring from the theme, while a cell or row with the ref keeps its layout (a linked number there is data); one part keeps one number across drawings; another number is a warning, not a failure, since text may mention a number near a ref. Measured values stay label and edge-label text. Schematic parts already carry their names as tags.
- A schematic is a netlist, never a drawing: one part per line with the nets it joins by name, placed by an offset from a pin of another part (`b@Q1.c 0,-1`), so the wiring drawn is the wiring stated. `src/schematic/route.ts` wires the nets on a 10-unit grid (A*, no ELK, no second dialect) and `check.ts` fails `pack` (`schematic block n: line N (ID): ...`, each saying what to write) on wires through parts, overlaps, labels far from or nearer another part than their own, unmeant contacts (a part's leads are conductor of their pin, so a pin or wire end of another net on one is a contact, and an `nc` pin that touches anything, even another `nc` pin, is one) and nets that fall in pieces or join one pin (`nc` leaves a pin open on purpose). Symbols carry `marks` (a polarity sign) that wires and parts stay out of like the body, and the router records every grid point of a routed wire, not its corners only. The drawing is one inline SVG in `currentColor`; each part is a `<g data-ref=NAME>`, each wire and junction carries its net and the parts it joins, every ground `gnd`. Grounds always hang down (a ground pin that faces up is an error telling the author to turn the part), and a label must be strictly nearer its own part than any other. It fills the column up to part names at 13 px, or wider where that keeps its smallest text at 10 px (`--schematic-max`), keeps 10 px text on phones and scrolls sideways below that (`--schematic-min`), and fits the paper in print.
- Controls set states by ref. kit:link.js is the one writer of `data-state` on `[data-ref]` elements: it joins the declarations in `data-ref-states` (a JSON map of ref to state, "" for none) that steps.js writes on a stepper for its captions' `data-refs` (now, not-yet) and an Explore's figure writes for its frame's `states`, and leaves alone an element no declaration names (a Table row's `fit`). pack writes the starting declarations' states into the file the same way (an element whose named refs have no state loses its `data-state`) and fails on a named ref no element carries, counting the filled records it draws as part of the page and naming the record's hash for a control inside one (`src/ref-states.ts`); a stepper declares nothing in the file, so it shows whole without scripts. State names are the page's to style; the kit styles only now and not-yet, on the elements link.js marks `data-kit-state` (now wins over not-yet; a page's own `data-state` stays unstyled), and print shows them like `data-step` parts. Explore and Controls refuse children rather than drop them: markup per frame is a client component's job.
- Linked parts share a screen. `.beside` (text, then a figure, diagram or code) stands side by side from 56rem, the text on the column's start like the prose around it and the figure out to `.wide`'s end (a diagram narrower than its share starts beside the text rather than centred away from it: #179), with the figure sticky beside the scrolling text; phones stack it, since a figure pinned over the text at 45% of a 390 px screen hid most of a flowchart or code block (#159). A list beside its drawing puts the list first, with each item carrying its parts' `data-ref` names; lay the drawing out tall for the pinned column. `check` warns about a schematic or Mermaid that scrolls sideways in that column, while allowing readable-width diagram scrolling elsewhere (`PAGE_JS` in `src/page-probes.ts`). On the light-desktop overview and views, it groups refs with a part no partner shares a screen with by the pair of places they link, with the count and up to three names (#265). Terms in running text (phrasing elements outside every SVG and `pre`) do not vouch for each other when the ref also links a figure, code or block; parts of one SVG or one `pre` are one place, and separate circuits that share a name are separate places (#169). A stepper with a part out of its captions' sight still warns separately. Sticky parts are measured by scrolling (`LINKED_JS` in `src/page-probes.ts`).

One placement runs in order, markers' labels, then line-end names (`ends.ts`), then notes, each avoiding the lines and every box placed before it (`place.ts` holds the shared costs); on a bar plot the bars and their values go first, and the markers' labels keep off them. ## Limits

Biome (pinned 2.6.2) enforces the quality baseline at error: cognitive complexity 15, function length 80 lines without blanks, file length 600 lines, no `any`, no non-null assertions, no `@ts-ignore`, no import cycles, no unused code. Suppressions need a rule-specific reason and are rare; today they are:

- `kit/*.ts` and `kit/parts/*/*.ts` (the kit scripts): each file is one IIFE (a part is one function that hangs on `window` for its entry) that keeps its names out of the page's global scope, so the function-length rule sees one long function. The code inside is split into small functions.
- `kit/theme.css` and `kit/parts/theme/*.css`: deliberate `!important` overrides (`[hidden]`, reduced motion, print) and selector orders whose properties are disjoint. Biome compares specificity only within one file, so the order across parts is checked by eye: the parts keep the cascade order of one stylesheet, and `theme.css` comes last.

Excluded by path: `kit/echarts.js`, `kit/parts/math/temml.css`, `vendor/` bundles and declarations (generated), HTML and Markdown.

TypeScript uses `erasableSyntaxOnly`: no parameter properties, enums or namespaces, so node can strip types in `cli.ts` and Bun's transpiler can strip them from the kit.

## The kit scripts

The kit scripts are TypeScript sources. Authors never name them: `src/mdx/kit-scripts.ts` picks the ones a page's markup needs, and the page shell refers to each as `kit:<name>.js` internally. `src/kit.ts` maps that name to the `.ts` file and `pack` strips the types with `Bun.Transpiler` as it inlines it: the output is a plain classic script (no imports, exports or module wrapper), with the file's leading `/* ... */` documentation comment put back in front, because the transpiler drops every comment. `kit <feature>` (for example `kit keep`) prints that comment from the source for the scripts the `kit` listing names; the others are documented through the components that bring them. Keep a kit file a script: no top-level `import` or `export`, no generated `.js` next to the source. Bun's transpiler is not a pure type eraser: it drops a `"use strict"` directive, rewrites top-level `this`, and adds an import for decorators, so the kit uses none of these and wraps its code in a function or assigns to `window`.

`tsconfig.kit.json` checks them with the DOM lib, no Bun types and the same strict options as the rest, except `noPropertyAccessFromIndexSignature`: `element.dataset` has an index signature, so the option would turn every `dataset.ref` into `dataset["ref"]`, which Biome's `useLiteralKeys` rejects. The window globals the scripts define (`Charts`, `Plot`, `Steps`, `Views`, `Keep`, `ReplyNotes`, and the parts pack runs too, `ChartsOption` and `PlotDraw`) and `echarts` are declared once in `kit-types/globals.d.ts`, with the option and callback types of their public API. Authors can typecheck their own `.tsx` with `kit types > tsconfig.json` then `bun --check`; the generated config resolves the components and the vendored Preact, ECharts and kit declarations without an install.

## The MDX pipeline

- **The runtime stays the attribute kit.** The kit scripts and `theme.css` are the tested behaviour; the components in `kit/components/` are typed markup generators over them, rendering the markup the scripts read (`section.view[data-view]`, `[data-stepper]` with `[data-captions]`, `fieldset[data-reply]`, `.tree` of nested `<details>`, `.chart`). Records is the one exception that owns its state: an island over the records core, drawing the `.tree` and `table.compare` markup, with views' folds (`kit/parts/views/folds.ts`) leaving its `<details>` alone. Keep runtime changes additive.
- **Static by default.** Everything in the MDX renders once at pack time, so static components take any props, functions included, except `onX` handlers, which would never run: pack fails on one made outside every island, naming the element and prop.
- **Islands.** The capitalised exports of a module whose first statement is `"use client"` hydrate in the browser. They render between `<!--island:N-->…<!--/island-->` with no wrapper element, so the theme's child selectors still match. Props from the page must be JSON or functions a `"use client"` module exports (pack fails with the prop path otherwise). Markdown between an island's tags is its slot: rendered once to static HTML, placed exactly once with `{children}`, and left untouched by re-renders; a `##` first in it starts the enclosing section. A kit client module (Chart, Plot) may sit in a slot as an island of its own; the author's own client component may not. charts.js and plot.js load before the islands (and echarts.js, compressed: see ECharts ships compressed); views, steps, link, keep and reply after, so they reach Preact-owned DOM and keep's restore fires the input and change events Preact's handlers read.
- **Navigation diagnostics.** `pack` and `check` advise on Markdown link syntax left in rendered text outside code; intentional examples use code markup. `check` treats missing in-page targets as problems (ids, named anchors and kit view routes count), and missing relative files as warnings, resolved beside the checked export; external links are never fetched. Navigation validation stays in `check`, where client-rendered targets and the export's final location are known, rather than rejecting pack's prerendered links. `src/link-probes.ts` owns these checks separately from layout probes.
- **Page shell and structure.** pack writes `<html lang>`, the title, the theme, the page's CSS, `<main class="page"><div data-overview>…</div>views…</main>`, the islands' props as JSON, `kitLabels`, then the scripts. `#` plus the paragraphs under it form `header.masthead` (the first `.lede`, one opening with a bold label the reader's `.next` action, the rest `.meta`); each `##` (or `<h2 data-nav>`) with what follows becomes a `<section>` unless the author wrote one; every rendered `View` moves after the overview. A GFM table becomes `table.compare` in a `div.scroll` (the box a phone scrolls it in at readable column widths; `Table` draws the same; first cell `<th scope="row">`, `data-label` per cell, `---:` columns `.num`).
- **A page in parts is one page** (#277). The parts' text is appended to the page's (`origins.ts`), so math's offset reads and the code, math and MDX errors name the part's file and line (a component missing at render still names the page). A part that cannot join stays a fragment compiled on its own, as before, and pack warns when its `#`/`##` then make no structure. A JSX tag starting with a small letter that names an import fails pack, since MDX writes it as an HTML element (#285).
- **The rail groups by `###`** (#281, owner 2026-11-22: Fumadocs-like, groups need not collapse). A section's `h3`s are its topics (beside a figure too; not a nested section's, a folded one's, or one whose id is a view name), section ids allocated before topic ids, indented under its entry on the trail lists' hairline; the spy marks the topic passed as the location (the one the address names while it sits in the top third or the page is at its end, else at the end the last in sight) and its section `.holds-current`, and scrolls the fixed rail only when the current entry changes and leaves its box, never against the reader's own rail scroll. Every `###` shows, on short pages too: the rail scrolls to the current entry, and collapsing other groups would move entries under the pointer as the reader scrolls.
- **Frontmatter:** `title`, `lang`, `labels` (`kit labels` prints every key), `reply: true` (notes on a page with no question), `replyTo` (an http(s) endpoint URL written as `<meta name="explainer-reply-to">`, which brings reply.js; see the reply channel), `scheme: light | dark`, `display: condensed` (kit:display.css and the Barlow Condensed font, only on that page; the cased words of a `#`, `##` or JSX `h1`/`h2`, in the page and in the `.mdx` fragments it imports, wrapped in `span.cased` so they keep their case under the capitals; code in a heading keeps its case by CSS), `contents: true` (the contents rail on a page without views, written as `<main data-contents>`); any other key fails. pack warns on a non-English `lang` without `labels`.

The contents rail of a page without views comes from its frontmatter (`contents: true`), not its markup: `page.ts` brings views.js for it. A new component needs a row only for an attribute or global no script read before; `kit` sizes each component by the same table. Markup built from computed names is not found.

Grid bounds in a media query's option stay the author's, since ECharts applies them again over a generated bottom. Provenance flags merge with the components to distinguish authored bounds from defaults; restore a generated `grid.bottom` before an author's next update, never over their `height`.
- **Series names are never a legend** (#190, user 2026-11-20). An author's legend (`legend: true`) and the picked key stay; a Chart shows a legend only when its option sets one.

One 1 s budget per page call, checked inside every loop, bounds thousands of labels on one spot, and a figure it cuts short says so.

Probe fixed-media interval endpoints and exact inclusive media boundaries, using ECharts' rounded width/height predicates for aspect ratios; phone and half ranges exclude their upper CSS boundary. - **ECharts ships compressed.** Page size is not a budget; the size test only catches the runtime shipped uncompressed or twice.
  `pack` inlines `kit/echarts.js` (931 KB) as deflate-raw in base64 (`data-deflate` on the script, 418 KB), with its licence comment and `kit/unpack.ts` as the script text. The loader inflates it with `DecompressionStream`, runs the text as a script, and sets `window.echartsReady`, a promise of `echarts` existing. It runs in order but async, so the scripts after it start before ECharts exists: `charts.js` defines `Charts` at once (it accepts a pending `echartsReady` in place of `echarts`), and `Charts.make` mounts a chart only after the font and `echartsReady`, so the drawn chart stays until the live one replaces it and a page's `Charts.make` call needs no change. Code that uses the `echarts` global directly must run after a chart's `setup` or `await echartsReady`. `check`'s wait (`SETTLE_JS`) waits for `echartsReady` too. The encoding ties for smallest on the Chrome 103, Firefox 113 and Safari 16.4 baseline: deflate-raw and gzip both give 313 KB (base64 418 KB); Brotli is smaller at 258 KB (base64 344 KB) but `DecompressionStream` does not read it in those baseline versions, and bytes as Latin-1 text (470 KB) cost more than base64 in UTF-8; these sizes are ECharts 6.1.0's as `examples/echarts-compressed/measure.ts` measures them, and drift with the ECharts version. The unpack is 31 ms of work (atob 11, inflate 3, parse and run 17). Other inlined code was measured and left plain: the island bundle (60 to 300 KB) must run before the views and steps scripts and would delay them, and CSS cannot wait for a script. A browser without `deflate-raw` support (before Chrome 103, Firefox 113, Safari 16.4) keeps the drawn charts and logs the failure.

The strip's short forms are generated content (`data-short`), so reply and keep read one label.
- **Code fences** are drawn at pack time like math: `src/mdx/code.ts` splits every `pre > code` into `span.code-line`s (with `--indent`, its leading whitespace, so a line wrapped on a phone or paper continues under its own start) and, for a language refractor knows, token spans in eight `tok-` classes that `kit/code.css` colours from the kit's tokens (mixed with `--ink`, so each class keeps 4.5:1 on `--sunken` and on lit code's `--accent-soft` in both schemes; lit code adds an accent outline rather than a darker tint); an unknown language stays plain but keeps its lines. A diff fence's lines carry their kind (`code-inserted`, `code-deleted`, tinted across the listing; a unified hunk's lines are the ones its header counts, so `---i;` in one is a change, and lines outside a hunk read as Prism's diff grammar reads them), and `--indent` counts from after the marker; ```` ```diff-<language> ```` (Prism's naming) colours the code after the markers in that language, reading the old side (context and deleted lines) and the new side (context and inserted lines) of each hunk or file each as one listing, so a string or comment over several lines stays one and does not run into the next hunk, and `pack` fails on a language refractor does not know (#262). `kit:code.css` carries the line layout, the lit-code rule and the token colours, and comes with any page that has a fence, decided as kit scripts are: in the prerendered HTML or the client code (a fragment an island renders later, a filled view's records); a page without one pays nothing, and `theme.css` keeps only `pre`'s tab size and phone wrap. refractor was chosen by measurement: 152 KB minified for its common languages plus TSX and VHDL, pure JS, hast out; Shiki with its JavaScript regex engine was 997 KB for ten grammars, and highlight.js (65 KB) has no TSX and misreads JSX attributes. A fence's meta takes only `ref:name="text"` marks, which wrap every occurrence in `<span data-ref>`; a mark the code does not hold, a partial overlap or any other meta fails the pack at the fence's line. A `pre` is one place for link.js, as an SVG is, so marks link only to a partner outside their fence. Lines are inline blocks so tabs measure in the code's font (tab stops follow the nearest block container's font, and `pre code` is smaller than `pre`).
- **Math** renders at pack time to MathML with Temml: no script ships, display math scrolls sideways on a phone, `kit/math.css` comes only with a page that has math. `Explore` precomputes frames when its `frame` is not a client export, refusing over 100,000 JSON characters.
- **A new component** is a module in `kit/components/` re-exported from `index.ts`, with a leading `Name: description` comment (the listing line; `kit <Name>` prints the comment). `test/mdx-islands.test.ts` fails for an export without a use in `COMPONENT_USES`, and for one whose later render brings fewer scripts than its static render. `test/fixtures/mdx-all/` should use it.

## Installing

Verified with `npx skills` 1.7.4 and Caplet 0.1.0 (the first npm release, `@caplet/cli`): both copy every file byte for byte (npx skills symlinks the other agents to one canonical copy when several are chosen), and `kit`, `pack`, `check` and the example's `kit types` + `bun --check` run from the installed copy with no install step. `bun run verify:install` repeats this from a clone of HEAD (uncommitted changes are not tested); run it before a release and whenever `skills/explainer/` changes shape (new top-level file, dotfile, `package.json`).

npx skills installs from any public git repository; the skills.sh listing comes from its install telemetry, so the skill appears there after people install it. Caplet takes `github:<owner>/<repo>` or `git:<url>` with a required `--pin <ref>`: a branch to follow or a tag for a fixed version.

Trying an installer by hand: always give it a disposable HOME (installers write to `~/.agents`, `~/.claude` and, for npx skills, `~/.agents/.skill-lock.json`), with `DISABLE_TELEMETRY=1` and `CLAUDE_CONFIG_DIR` unset. Caplet quirks that matter:

- A project-scope Caplet command with no `.agents/` in the project walks up the directory tree. A sandbox below the real home therefore finds the real `~/.agents` and writes to it. Run `caplet init` in the project first (`verify-install.ts` does).
- `caplet add` does not detect that another capability already emits a skill of the same name. Both write into one directory, the files mix, and `caplet check` stays stale. Retire the other source first.
- A local-path source is snapshotted: after changing the checkout run `caplet update explainer`, not `caplet apply`.
- Caplet rewrites `SKILL.md`'s frontmatter as YAML folded at 80 columns with no blank line after it. `SKILL.md` is kept in that form so Caplet's copy stays byte-identical; after editing the description, run `verify:install` or fold it the same way.
- Caplet gives Claude Code the skill as a plugin, not as `~/.claude/skills/explainer`: the copy Claude Code loads is the `installPath` in `~/.claude/plugins/installed_plugins.json` (plus `skills/explainer`), which `verify-install.ts` reads.

## Changing the kit

Kit files are behaviour, not just code. After a change: `pack` then `check` `skills/explainer/example/page.mdx` and a few real pages (light and dark, 1440 and 390 wide are covered by `check`), open the screenshots, and compare with the previous output. Pages reference local files relative to themselves, so pack them from where they are with `-o` elsewhere.

## Tracking

Open work lives in [GitHub Issues](https://github.com/barisgit/explainer-skill/issues), not in files. File a finding as an issue with the symptom, `Path:`, `Suspected cause:` and what counts as done. Label it with one `type:`, its `area:` labels (`kit`, `cli`, `check`, `pack`, `install`, `ci`), a `priority:` or `status:deferred`, and `invariant` when it breaks a decision or promise in this file or the docs; `status:needs-decision` marks an issue waiting on a product choice. A fixing commit closes its issue. Deferred issues are not authority to build.

## Commits

Conventional Commits (`feat(kit):`, `fix(check):`, `chore:`, `test:`, `docs:`), one change per commit, explicit paths when staging. Gates pass on every commit. The public remote is `github.com/barisgit/explainer-skill` (MIT); releases are tags such as `v0.1.0`, which Caplet installs pin.

## Pull requests

Lead with **What changed and why**. Under **Evidence**, link the covering test files at the PR's head SHA and the CI run for that exact head. For visible changes, show before and after in light and dark, on desktop and phone where layout matters. For an interaction, include an animated WebP. Say what was not verified.

Keep PR media off `main`: put it on the orphan `pr-media` branch under `<pr-branch>/` and embed it as `https://github.com/barisgit/explainer-skill/blob/pr-media/<pr-branch>/<file>?raw=true`. GitHub renders PNGs and animated WebPs inline; a repo-relative `<video>` does not play. Keep clips small: capture a few frames with `check --do shot:<css>` and encode them with ffmpeg's `libwebp_anim`, as the [encoder](build/media/encode.ts) used by `build/media.ts` does. If a push to `pr-media` is rejected because it advanced, fetch, rebase your media commit onto it and push again; never force-push it. Commit media from a worktree of `pr-media` (`git worktree add .worktrees/pr-media pr-media`): the hook path `.husky/_` does not exist there, so no hook runs and `--no-verify` is never needed.

## Working in parallel

Each change lives on its own branch in its own worktree (a Superset workspace, or `.worktrees/<name>`, which is ignored) and lands on `main` as a fast-forward once GitHub CI on its pull request passed on the exact head. A pull request that conflicts with `main` gets no CI run and no failure signal (`gh pr view <n> --json mergeable` shows it), so bring the branch up to date first. Every test page launches Chrome, so locally run the test files you touched, lint and the typecheck, and let the pull request's CI run the full gate: two full suites at once slow each other and the machine. Run one Chrome-driving command at a time, and leave no Chrome, profile or scratch directory behind.

## Releasing

Before 1.0, a release that changes what an author writes or gets bumps the minor version, a fix the patch.

1. Rename the CHANGELOG's `## Unreleased` to the version, and update the pinned tag in the README's Caplet example.
2. After kit changes, repack and `check` the examples, then `bun run media` on a machine whose ffmpeg has libwebp_anim (Homebrew's lacks it; Debian's has it). Commit regenerated cards and clips when the pages or recording scenes changed.
3. Push, and once CI on that commit passed, tag it (`git tag -a vX.Y.Z -m vX.Y.Z`) and publish `gh release create vX.Y.Z --verify-tag --notes-file` with that version's CHANGELOG section.
4. Run `bun run verify:install` when `skills/explainer/` changed shape (see Installing).
