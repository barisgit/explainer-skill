# Explainer skill: agent instructions

An agent skill, `explainer`, that builds one self-contained, interactive HTML page (charts, diagrams, step-through figures, drill-down views, reader replies) that works offline from `file://`. The skill is a thin `SKILL.md` plus a CLI (`kit`, `pack`, `check`) that the agent drives.

## Requirements

- Bun 1.4.3 (`curl -fsSL https://bun.sh/install | bash`). The CLI uses Bun's built-in `HTMLRewriter` and `import.meta.dir`; there is no npm install step for users. `node skills/explainer/cli.ts` prints an install hint and exits 2.
- Google Chrome or Chromium for `check` (`CHROME=/path` overrides the search, which also finds agent-browser and Playwright downloads; CI uses the runner's Chrome). `src/chrome.ts` retries without the sandbox when Chrome reports none is usable.

## Layout

```text
skills/explainer/      the installable skill, copied as-is by installers: no dotfiles, tests or node_modules inside
  SKILL.md guide.md example.html
  cli.ts               thin entry: Bun check, then imports src/main.ts (erasable syntax only, so node can run it far enough to explain)
  src/                 main.ts (dispatch, help), commands.ts (one spec per command), paths.ts, kit.ts (kit file names, TypeScript to script, the kit's CSS layer), pack.ts, collisions.ts (page classes the kit styles too), loads.ts (what a packed page would still load, read through Bun's CSS parser), svg-theme.ts (svg files per colour scheme), check.ts, steps.ts, report.ts, mermaid.ts, chrome.ts (CDP client)
  kit/                 what pages reference as kit:<file>: theme.css, charts, plot, steps, link, views and reply as .ts sources that pages name .js, echarts.js (generated), fonts/, licenses/
    parts/<name>/      pieces of a kit file too long for one file (a script, or theme.css by concern); pack puts them in front of kit/<name> in file name order, so a page still includes one file
  vendor/beautiful-mermaid.js  generated (beautiful-mermaid, patched, with ELK); used by pack to render diagrams in-process, never inlined; its .d.ts beside it
build/                 vendor.ts regenerates kit/echarts.js, vendor/beautiful-mermaid.js and the licence texts from the pinned devDependencies; geist-widths.ts measures the Geist advances the patch sizes diagram text with; verify-install.ts is the release check for the installers; media.ts (with media/) renders the README and gallery media
test/                  contract tests, outside the skill so installs do not ship them
kit-types/             globals.d.ts: the window globals the kit scripts define (and echarts), for the kit typecheck only; outside the skill so installs do not ship it
examples/              the public gallery, published as it is committed by .github/workflows/pages.yml (push to main)
  page.html index.html the gallery page and its packed output
  <name>/              one showcase page: page.html (written by an agent following SKILL.md), index.html (packed), its local data
  media/               generated by bun run media: hero, gallery thumbnails, README clips, each as <name>-light.webp and <name>-dark.webp
```

Root files: `package.json` (devDependencies only), `bun.lock`, `patches/` (the beautiful-mermaid patch, applied by `bun install`), `tsconfig.json` (the CLI, build and tests; Bun types), `tsconfig.kit.json` (the kit scripts; DOM lib, no Bun types), `biome.json`, `bunfig.toml`, `.husky/`, `.github/workflows/ci.yml` and `pages.yml`.

Showcase assets stay in `examples/`, never in `skills/explainer/`, because installers copy the skill folder. After changing a page or the kit, repack the examples (`pack page.html -o index.html` from each directory), `check` each to 0 problems, then `bun run media`; GitHub renders the repo-relative animated WebP clips in the README, while a repo-relative `<video>` does not play. The README picks each image's theme with `<picture><source media="(prefers-color-scheme: dark)">`; the gallery shows both thumbnails and hides one with CSS, as the kit does for SVG files in `<img>`.

## Commands

| Command | What it does |
|---|---|
| `bun install` | Installs dev tools from the lockfile and the git hook (`prepare` runs husky) |
| `bun run typecheck` | `bun check --all` for the CLI, build and tests, then for the kit (`tsconfig.kit.json`): Bun's built-in checker, same errors as `tsc`, strictest settings |
| `bun run lint` | `biome check` (format check, lint, import order), warnings are errors; no writes |
| `bun run format` | `biome check --write`: formats and applies safe fixes |
| `bun run test` | Contract tests (Chrome needed, about two minutes) |
| `bun run ci` | typecheck, lint, test: the gate; the same command runs in GitHub Actions |
| `bun run verify:install` | Release check, not in `ci` (needs network and Chrome): installs from a clone of HEAD with `npx skills` and Caplet into a temp HOME, then runs `kit`, `pack`, `check` from each copy |
| `bun run media [--keep] [example ...]` | Regenerates `examples/media/` (gallery thumbnails, hero collage, animated WebP clips) in light and dark from the packed `examples/<name>/index.html` pages; a full run replaces the directory. Scenes are data at the top of `build/media.ts`. Needs Chrome and ffmpeg with libwebp_anim; about two minutes |
| `bun run vendor` | Regenerates the ECharts bundle, the beautiful-mermaid bundle and the licence texts (dev only) |
| `bun skills/explainer/cli.ts kit \| pack \| check` | The skill's CLI; `--help` on any command |

The pre-commit hook (husky + lint-staged) runs Biome with fixes on the staged files, then the typecheck; about 2 s, no Chrome. It keeps partially staged hunks. lint-staged backs up through `git stash`, which worktrees share, so run commits of different worktrees one at a time. Never use `--no-verify`.

`.github/workflows/ci.yml` runs `bun install --frozen-lockfile` and `bun run ci` on ubuntu-latest. The runner restricts user namespaces, so CI exercises the no-sandbox retry.

## Decisions

- One skill named `explainer`: thin `SKILL.md` and the CLI as the toolbox; no custom elements; offline single-file output; the house style lives in `kit/theme.css` (with `kit/parts/theme/`) and `example.html`, not in instructions.
- Runtime is Bun only. Headless Chrome (CDP over WebSocket, no Puppeteer) for `check` only.
- Mermaid is rendered in-process by beautiful-mermaid with ELK: one SVG per diagram, drawn with the renderer's variables that `theme.css` maps to the kit tokens, so it follows light, dark and a page's overrides. The patch (`patches/beautiful-mermaid@1.1.3.patch`) lays out in reading order, sizes text with Geist's measured widths and wraps labels at Mermaid's 200 px. `pack` fails, with what to write instead, on types it cannot draw and on input the renderer would draw wrong silently. Diagrams do not step; linked highlighting walks through them.
- Layout is the packaging layout above: Caplet imports `skills/*/SKILL.md` as a bare skill and copies every non-hidden file. Do not add an `acf.yml`; it would make Caplet emit only the files listed in `assets:`.
- Agent-facing text (SKILL.md, guide.md, kit file headers, CLI help) stays short and soft. A kit file's leading comment is its documentation: `kit <file>` prints it, and its first line (`name: description`) is the listing.
- The kit's CSS ships in `@layer kit` (`readKitText` wraps it, internal order kept), so a page's own unlayered CSS always wins and one plain rule overrides the kit. The kit's `!important` rules (`[hidden]`, reduced motion, print, the other copy of an SVG file) therefore also beat a page's `!important`. The kit's other properties still reach a page element that carries a kit class, so `pack` warns when a page rule styles an element by a class the kit styles on its own (`collisions.ts` states the rule); the documented classes are no exception, since `.tree` was one when a page's own `.tree` was restyled (#51).
- `pack` themes an SVG file in `<img>` without reading it as markup: the file stays an image (no script, network or page styling reaches it), packed twice as `img.light` and `img.dark` with a first `:where(:root)` rule that sets `color-scheme`, `color: var(--ink)` and the colour tokens copied from `theme.css`, and `theme.css` shows the copy for the scheme. A page's own token overrides do not reach the file; parts that must link or respond need inline SVG.
- Credits stay: visual-explainer (MIT, Nico Bailon), ECharts (Apache-2.0), beautiful-mermaid (MIT, Craft Docs) with elkjs (EPL-2.0) and entities (BSD-2-Clause), Geist fonts (OFL); their licence texts ship in `kit/licenses/`. EPL-2.0 needs the source statement in `elkjs.txt` and the notice in the bundle header, both written by `build/vendor.ts`.
- No local-only dependencies at runtime: nothing but `kit/` and `vendor/` is needed after install, and Chrome for `check`.

## Limits

Biome (pinned 2.6.2) enforces the quality baseline at error: cognitive complexity 15, function length 80 lines without blanks, file length 600 lines, no `any`, no non-null assertions, no `@ts-ignore`, no import cycles, no unused code. Suppressions need a rule-specific reason and are rare; today they are:

- `kit/**/*.ts`: each file is one IIFE (a part is one function that hangs on `window` for its entry) that keeps its names out of the page's global scope, so the function-length rule sees one long function. The code inside is split into small functions.
- `kit/theme.css` and `kit/parts/theme/*.css`: deliberate `!important` overrides (`[hidden]`, reduced motion, print) and selector orders whose properties are disjoint. Biome compares specificity only within one file, so the order across parts is checked by eye: the parts keep the cascade order of one stylesheet, and `theme.css` comes last.

Excluded by path: `kit/echarts.js`, `vendor/beautiful-mermaid.js` (generated), HTML and Markdown.

TypeScript uses `erasableSyntaxOnly`: no parameter properties, enums or namespaces, so node can strip types in `cli.ts` and Bun's transpiler can strip them from the kit.

## The kit scripts

The kit scripts are TypeScript sources, but pages reference them as `kit:<name>.js`. `src/kit.ts` maps the name to the `.ts` file and `pack` strips the types with `Bun.Transpiler` as it inlines it: the output is a plain classic script (no imports, exports or module wrapper), with the file's leading `/* ... */` documentation comment put back in front, because the transpiler drops every comment. `kit <file>` prints that comment from the source. Keep a kit file a script: no top-level `import` or `export`, no generated `.js` next to the source. Bun's transpiler is not a pure type eraser: it drops a `"use strict"` directive, rewrites top-level `this`, and adds an import for decorators, so the kit uses none of these and wraps its code in a function or assigns to `window`.

`tsconfig.kit.json` checks them with the DOM lib, no Bun types and the same strict options as the rest, except `noPropertyAccessFromIndexSignature`: `element.dataset` has an index signature, so the option would turn every `dataset.ref` into `dataset["ref"]`, which Biome's `useLiteralKeys` rejects. The window globals the scripts define (`Charts`, `Plot`, `Steps`, `Views`, `ReplyKeep`, `ReplyNotes`) and `echarts` are declared once in `kit-types/globals.d.ts`, with the option and callback types of their public API. Pages that agents write are not checked.

## Installing

Verified with `npx skills` 1.7.4 and Caplet 0.2.0: both copy every file byte for byte (npx skills symlinks the other agents to one canonical copy when several are chosen), and `kit`, `pack` and `check` run from the installed copy with no install step. `bun run verify:install` repeats this from a clone of HEAD (uncommitted changes are not tested); run it before a release and whenever `skills/explainer/` changes shape (new top-level file, dotfile, `package.json`).

npx skills installs from any public git repository; the skills.sh listing comes from its install telemetry, so the skill appears there after people install it. Caplet takes `github:<owner>/<repo>` or `git:<url>` with a required `--pin <ref>`: a branch to follow or a tag for a fixed version.

Trying an installer by hand: always give it a disposable HOME (installers write to `~/.agents`, `~/.claude` and, for npx skills, `~/.agents/.skill-lock.json`), with `DISABLE_TELEMETRY=1` and `CLAUDE_CONFIG_DIR` unset. Caplet quirks that matter:

- A project-scope Caplet command with no `.agents/` in the project walks up the directory tree. A sandbox below the real home therefore finds the real `~/.agents` and writes to it. Run `caplet init` in the project first (`verify-install.ts` does).
- `caplet add` does not detect that another capability already emits a skill of the same name. Both write into one directory, the files mix, and `caplet check` stays stale. Retire the other source first.
- A local-path source is snapshotted: after changing the checkout run `caplet update explainer`, not `caplet apply`.

## Changing the kit

Kit files are behaviour, not just code. After a change: `pack` then `check` `skills/explainer/example.html` and a few real pages (light and dark, 1440 and 390 wide are covered by `check`), open the screenshots, and compare with the previous output. Pages reference local files relative to themselves, so pack them from where they are with `-o` elsewhere.

## Tracking

Open work lives in [GitHub Issues](https://github.com/barisgit/explainer-skill/issues), not in files. File a finding as an issue with the symptom, `Path:`, `Suspected cause:` and what counts as done. Label it with one `type:`, its `area:` labels (`kit`, `cli`, `check`, `pack`, `install`, `ci`), a `priority:` or `status:deferred`, and `invariant` when it breaks a decision or promise in this file or the docs; `status:needs-decision` marks an issue waiting on a product choice. A fixing commit closes its issue. Deferred issues are not authority to build.

## Commits

Conventional Commits (`feat(kit):`, `fix(check):`, `chore:`, `test:`, `docs:`), one change per commit, explicit paths when staging. Gates pass on every commit. The public remote is `github.com/barisgit/explainer-skill` (MIT); releases are tags such as `v0.1.0`, which Caplet installs pin.
