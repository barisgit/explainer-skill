# Explainer

The page exists so a reader understands the most with the least effort and time, and enjoys it: the big picture first and kept in sight, pictures before words, every click showing something new. A wall of text, or a page that needs many clicks before anything shows, fails that whatever else it gets right.

The first route fits the reader's knowledge, goal and available time from the request; ask when unknown and it would change the page. One short answer leads the page; when the reader has a task to carry out, that section comes first, with what it depends on. Novices get brief orientation, experienced readers a quick route, and a reader new to the project its context however expert they are; the main path stays short, the rest reference. A lost or time-pressed reader needs one task at a time, not a whole course, and unfamiliar material needs a worked example before practice. Each section answers one question. Keep sets readers work through complete. Put each item they judge whole beside its evidence and reply question: for generated artifacts, show the actual variants or matched excerpts.

By default a figure, table or diagram carries each section's answer, with prose interpreting it, qualitative subjects too: a system as a map of its parts, a state or divergence as a Mermaid flowchart, what each side has as a matrix with a status column, a history as a timeline (a flowchart LR, one node per period), a process as a flow. Before writing, plan the figures: name for each section, and each part or view, the diagram or chart that carries it; text interprets the figures, it does not replace them. Add interaction only where it answers a reader's question or captures a decision. Leave out what does not serve the reader's goal, whether deciding, understanding or acting. Draw on every source that describes the subject, such as a work list, spec or requirements, not only the one with the numbers. Bring real images in locally and link claims to sources: offline means no network needed, not no links. Keep claims no stronger than their sources and distinguish the page's own reasoning. Give the reader the packed file or its link rather than embedding it in a host's inline frame: the page assumes a browser window.

Guidance on design, wording, or presentation from the user, the project, or another skill you have loaded wins over this skill's defaults. Restyle the kit through its tokens rather than replacing it.

Work with the CLI next to this file, run as `bun <this-directory>/cli.ts`:

1. Read `guide.md` next to this file: a short list of what made earlier pages better or worse. `example/page.mdx` is one short, finished decision page and `example/tour/page.mdx` a short tour of a whole system, its parts in views; both use the kit where it helps their subject: read them for technique, not as layouts to copy.
2. Write `page.mdx`: Markdown prose, the kit's tags, and `.ts` or `.json` data it imports. Run `kit` to list what a page can use, and `kit <name>` for each you use: interactive ECharts in the page theme (`Chart`, or the light `Plot` for a few small plots), sliders and switches over figures (`Explore`, `Controls`), tables from data (`Table`), Mermaid diagrams written as ```` ```mermaid ```` fences, circuits as ```` ```schematic ```` netlists, TeX formulas, the stylesheet, drill-down views (`View`), records as a grouped tree, sortable table or board (`Records`), step-through figures (`Stepper`), linked highlighting between prose, rows, diagram parts and marked code in coloured code fences, questions the reader checks on the spot or answers in a reply with notes (`Question`), and reminders of a prerequisite opened at its term (`Recall`). Build from these before writing your own scripts and styles: hand-made bars, toggles, and saved state tend to miss the dark theme, phones, and keyboard use that the kit already handles. Only behaviour no tag covers needs a `.tsx` component whose first line is `"use client"`.
3. `pack page.mdx -o artifact.html` renders the page, diagrams and formulas included, into one offline file.
4. `check artifact.html` loads the page in light and dark at desktop and phone widths, checks layout and kit controls, and reports errors, console warnings, network use and overflow. `--view all` checks every drill-down view. `--do` runs specific interactions instead of sampling controls; `--do reply` prints the current reply without copying or sending it. Use `--shots` to save and inspect PNGs when judging the visual result or investigating a layout problem; `--do shot:<css>` saves just the element. Reread `page.mdx` against the guide's Words, Reminders, Tasks and pitfalls, and Study material points, which first drafts tend to miss. Then follow the first route as the intended reader: can they start without reading all the context, learn what the first control reveals, and answer beside the evidence with choices that fit? Check the remaining questions without hunting across views; a clean check cannot tell you that. Then cut: remove each sentence, subtitle or intro whose absence loses nothing, and reread.
5. When the page asks the reader questions (or has `reply: true`) and you want the answers back, `serve artifact.html --wait` serves it at a URL to give the reader, prints their reply once they send it, and exits; without `--wait` it prints each reply as it arrives. Repack and serve again after a change: the URL stays, so the reader keeps unsent answers. `serve` listens on this machine only; `--host 0.0.0.0` opens it to your network, where anyone who reaches it can read the page and reply (no accounts), so use it only on a trusted network, and a tunnel or a host running the same handler for readers further away. A copy sent by file or email needs `replyTo` in the frontmatter (`kit page`).
