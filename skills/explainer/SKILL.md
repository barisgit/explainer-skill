# Explainer

The first route fits the reader's knowledge, goal and available time from the request; ask when unknown and it would change the page. One short answer leads the page; when the reader has a task to carry out, that section comes first, with what it depends on. Novices get brief orientation, experienced readers a quick route, and a reader new to the project its context however expert they are; the main path stays short, the rest reference. A lost or time-pressed reader needs one task at a time, not a whole course, and unfamiliar material needs a worked example before practice. Each section answers one question. A set readers work through stays complete; items they must judge sit whole beside their evidence and reply questions.

By default a figure, table or diagram carries each section's answer, with prose interpreting it, qualitative subjects too: a state or divergence as a Mermaid flowchart, what each side has as a matrix with a status column, a history as a timeline (a flowchart LR, one node per period), a process as a flow. Add interaction only where it answers a reader's question or captures a decision. Leave out what does not serve the reader's goal, whether deciding, understanding or acting. Draw on every source that describes the subject, such as a work list, spec or requirements, not only the one with the numbers. Bring real images in locally and link claims to sources: offline means no network needed, not no links. Keep claims no stronger than their sources and distinguish the page's own reasoning. Give the reader the packed file or its link rather than embedding it in a host's inline frame: the page assumes a browser window.

Guidance on design, wording, or presentation from the user, the project, or another skill you have loaded wins over this skill's defaults. Restyle the kit through its tokens rather than replacing it.

Work with the CLI next to this file, run as `bun <this-directory>/cli.ts`:

1. Read `guide.md` next to this file: a short list of what made earlier pages better or worse. `example/page.mdx` is one short, finished decision page (hence its answer headings) that uses the kit where it helps its subject; read it for technique, not as a layout to copy.
2. Write `page.mdx`: Markdown prose, the kit's tags, and `.ts` or `.json` data it imports. Run `kit` to list what a page can use, and `kit <name>` for each you use: interactive ECharts in the page theme (`Chart`, or the light `Plot` for a few small plots), sliders and switches over figures (`Explore`, `Controls`), tables from data (`Table`), Mermaid diagrams written as ```` ```mermaid ```` fences, circuits as ```` ```schematic ```` netlists, TeX formulas, the stylesheet, drill-down views (`View`), records as a grouped tree, sortable table or board (`Records`), step-through figures (`Stepper`), linked highlighting between prose, rows, diagram parts and marked code in coloured code fences, questions the reader checks on the spot or answers in a reply with notes (`Question`), and reminders of a prerequisite opened at its term (`Recall`). Build from these before writing your own scripts and styles: hand-made bars, toggles, and saved state tend to miss the dark theme, phones, and keyboard use that the kit already handles. Only behaviour no tag covers needs a `.tsx` component whose first line is `"use client"`.
3. `pack page.mdx -o artifact.html` renders the page, diagrams and formulas included, into one offline file.
4. `check artifact.html` screenshots light and dark at desktop and phone width into a temp directory it prints, and reports errors, console warnings, network use, and overflow; `--view all` also captures every drill-down view, and `--do` clicks, drags, types or sets fields instead of the default bounded kit-control sample; `--do shot:<css>` saves one element; `--do reply` prints the current reply Markdown without copying or sending it (also in `--json`). Look at the screenshots and fix what you see. Then read the page top to bottom as the intended reader, who has not seen the sources, and fix where they stumble: does the first screen say what they will get; is each term, rule or step explained before a sentence, figure or task uses it; does a practice answer show before they try (in a worked example, a table, or a control's starting state); can they skip what they know and find a detail by its heading or fold; can they answer beside the evidence without hunting across views? A clean check cannot tell you that.
5. When the page asks the reader questions (or has `reply: true`) and you want the answers back, `serve artifact.html --wait` serves it at a URL to give the reader, prints their reply once they send it, and exits; without `--wait` it prints each reply as it arrives. Repack and serve again after a change: the URL stays, so the reader keeps unsent answers. `serve` listens on this machine only; `--host 0.0.0.0` opens it to your network, where anyone who reaches it can read the page and reply (no accounts), so use it only on a trusted network, and a tunnel or a host running the same handler for readers further away. A copy sent by file or email needs `replyTo` in the frontmatter (`kit page`).
